Testing and Regression Prevention

Refitter turns third-party OpenAPI documents, which vary a lot in quality and style, into C# that has to compile under several target frameworks and work with Refit at runtime. A string comparison of generated output can't prove that. Refitter's tests are therefore layered: fast unit tests, scenario tests that compile the generated code, runtime checks through Refit, tests of the real NuGet packages, smoke tests against real-world specifications, and nightly tests of the published packages.

Refitter.Tests

src/Refitter.Tests is the main test project: roughly 330 test files and over 2,500 test methods (many more test cases once [DataRow] expansions are counted).

  • Framework: MSTest v4 on Microsoft.Testing.Platform. The project is an executable (OutputType=Exe, EnableMSTestRunner=true).
  • Assertions: AwesomeAssertions (generatedCode.Should().Contain(...)).
  • Parallelism: [assembly: Parallelize(Scope = ExecutionScope.MethodLevel, Workers = 0)] runs test methods in parallel on every CPU core. Tests that touch global state use [DoNotParallelize]. Every test writes to its own GUID-named temporary folder, so tests don't interfere with each other.

Anatomy of a scenario test

Every new feature gets a scenario test in the Refitter.Tests.Scenarios namespace. The pattern is always the same: an OpenAPI specification as a const string, a generation step, string assertions, and a compilation check. A simplified version of ArrayTypeReturnTests:

[TestClass]
public class ArrayTypeReturnTests
{
    private const string OpenApiSpec = @"
openapi: '3.0.0'
paths:
  /jobs:
    get:
      responses:
        '200':
          content:
            application/json:
              schema:
                type: 'array'
                items:
                  $ref: '#/components/schemas/JobResponse'
...";

    [TestMethod]
    public async Task Returns_IList()
    {
        string generatedCode = await GenerateCode();
        generatedCode.Should().Contain("IList<JobResponse>");
    }

    [TestMethod]
    [TestCategory("Integration")]
    public async Task Can_Build_Generated_Code()
    {
        string generatedCode = await GenerateCode();
        BuildHelper.BuildCSharp(generatedCode).Should().BeTrue();
    }

    private static async Task<string> GenerateCode()
    {
        var swaggerFile = await SwaggerFileHelper.CreateSwaggerFile(OpenApiSpec);
        var settings = new RefitGeneratorSettings
        {
            OpenApiPath = swaggerFile,
            CodeGeneratorSettings = new CodeGeneratorSettings { ArrayType = "System.Collections.Generic.IList" }
        };
        var sut = await RefitGenerator.CreateAsync(settings);
        return sut.Generate();
    }
}

flowchart LR
    SPEC["const string OpenApiSpec"] --> FILE["SwaggerFileHelper.CreateSwaggerFile<br/>temp .yml / .json"]
    FILE --> GEN["RefitGenerator.CreateAsync(settings)<br/>.Generate()"]
    GEN --> A1["assert expected code IS generated"]
    GEN --> A2["assert replaced code is NOT generated"]
    GEN --> A3["BuildHelper.BuildCSharp<br/>[TestCategory Integration]"]

A test that only looks for a string can pass on code that doesn't compile, so the compilation check is required by the project's Definition of Done.

Compiling generated code: BuildHelper

BuildHelper checks that generated code compiles with a real dotnet build, against real package references:

sequenceDiagram
    autonumber
    participant Test
    participant BH as BuildHelper
    participant FS as Temp folder (GUID)
    participant Dotnet as dotnet build

    Test->>BH: BuildCSharp(generatedCode, ...)
    BH->>FS: write Project.csproj (template)
    BH->>FS: write Generated_0.cs, Generated_1.cs, ...
    BH->>Dotnet: dotnet build (child process)
    Dotnet-->>BH: exit code, stdout, stderr
    BH->>FS: delete folder
    alt exit code != 0
        BH-->>Test: throw BuildFailedException (with compiler output)
    else
        BH-->>Test: true
    end

The project template references Refit.HttpClientFactory, System.Text.Json, the Microsoft.Extensions DI, Polly and HTTP resilience packages and the Apizr packages, with XML documentation generation enabled. Variants cover other situations:

Method Builds
BuildCSharp(code) net8.0 (the lowest supported modern target)
BuildCSharp(warningsAsErrors: true, ...) With warnings treated as errors, for example to catch obsolete-member warnings from deprecated schemas or malformed XML documentation. Missing-documentation warnings (CS1591, CS1573) are suppressed in the template
BuildCSharpForTargetFramework("net9.0" / "net10.0" / "net11.0", ...) Newer target frameworks
BuildApizrCSharp Against the Apizr packages
BuildRefit11CSharp Against an older Refit major version
BuildCSharpWithoutImplicitUsings With implicit usings disabled, to catch missing using directives

Because these tests start dotnet build, they are much slower than the rest. The convention is to mark them [TestCategory("Integration")], but not every existing compilation test follows it yet (the real ArrayTypeReturnTests.Can_Build_Generated_Code has no category), so the filtered run is faster but not strictly free of dotnet build calls:

# build once
dotnet build -c Release src/Refitter.slnx

# tests not marked Integration
dotnet test --filter "TestCategory!=Integration" --solution src/Refitter.slnx -c Release --no-build

# full suite
dotnet test --solution src/Refitter.slnx -c Release

Checking runtime behaviour: RefitRequestCapture

Compiling is not the same as working. Refit validates interfaces when a client is created, and parameter attributes decide the URL, query string, headers and body of the request. RefitRequestCapture compiles generated code in memory with Roslyn (optionally running Refit's own source generator over it, to compare the generated-client and reflection code paths), creates a Refit client with a capturing HttpMessageHandler, calls a generated method and returns the HttpRequestMessage Refit produced. Tests then assert on the actual HTTP request.

Regression tests

Every bug fix comes with a test that fails without the fix. Small fixes add cases to the relevant scenario test; larger ones get a dedicated class in Regression/, named after the issue or symptom (for example ContractSuffixCorruptionTests, MalformedUnicodeEscapeTests, XmlDocEscapingTests). The smoke tests and MSBuild package tests also contain checks named after specific GitHub issues.

Source generator tests

src/Refitter.SourceGenerator.Tests (targeting net8.0, net10.0 and net11.0) tests the generator the way a consuming project uses it:

    subgraph TP["Refitter.SourceGenerator.Tests.csproj"]
        REF["ProjectReference Refitter.SourceGenerator<br/>OutputItemType=Analyzer<br/>ReferenceOutputAssembly=false"]
        IMP["Import Refitter.SourceGenerator.targets"]
        AF["AdditionalFiles/*.refitter<br/>(12 files)"]
    end
    AF --> GEN["Refitter generator<br/>+ nested Refit generator"]
    REF --> GEN
    IMP --> GEN
    GEN --> COMP["test assembly compiled<br/>with generated code"]
    COMP --> TESTS["tests use the generated types"]
  • The generator is referenced as an analyzer and its .targets file is imported explicitly, because a project reference doesn't import a package's build files. This makes the test build behave like a project consuming the NuGet package, including the Refit generator handoff.
  • The .refitter files cover multiple interfaces (by endpoint and by tag), optional parameters, Polly and HttpResilience, JsonSerializerContext, property naming policies, polymorphic serialization, custom output folders and two settings files with the same name in different folders (for hint name collisions).
  • Many checks happen at compile time: if the expected types weren't generated, the test project doesn't build. The tests then check namespaces, Refit HTTP attributes, that Refit's generated implementation (not reflection) is used, DI registration, serialization behaviour, and that the generator never writes files to disk.

Smoke tests

test/smoke-tests.sh (with a PowerShell equivalent, smoke-tests.ps1) exercises the CLI against real specifications and builds the result against many target frameworks.

    P0["Publish CLI from source<br/>(or use the published tool / Docker image)"] --> P1["Restore ConsoleApp solutions<br/>net462, net472, net48, net481, net8.0, net9.0, net10.0, net11.0"]

    P8 --> P11["Named regressions<br/>e.g. Asana spec, issue #359"]

    P2 -.-> BUILD["dotnet build of every consumer project"]
    P3 -.-> BUILD
    P5 -.-> BUILD
    P8 -.-> BUILD
  • Specifications: test/OpenAPI contains about 37 specifications across OpenAPI 2.0, 3.0 and 3.1, from small samples (Petstore, Uber, USPTO) to large real-world APIs (Asana, Mastodon, Ingram Micro, e-conomic, LM Studio).
  • Option variants: dozens of CLI option sets (cancellation tokens, internal types, IApiResponse, tag filtering, multiple interfaces, contracts only, interfaces only, and so on) are run against every specification.
  • Matrix builds use SmokeTest=true, which excludes generated JsonSerializerCtx*.cs files from compilation, so the JsonSerializerContext variants are only checked for successful generation there. Their compilation is covered by the unit tests in src/Refitter.Tests.
  • Target frameworks: generated code is compiled in console apps for .NET Framework 4.6.2 to 4.8.1 and .NET 8, 9, 10 and 11, which catches language features or APIs that aren't available on older frameworks.
  • The same script runs in three modes: from source (pr.yml, smoke-tests.yml, regression-tests.yml), against the published refitter tool (-UseProduction) and against the Docker image (-UseDocker).

Workflow What it guards against
build.yml Build breaks, warnings (treated as errors) and test failures. Runs the fast unit tests first so failures show up quickly, then the full suite
codecov.yml Untested code. Coverage is collected with Microsoft.Testing.Platform and uploaded to Codecov, which flags coverage drops
pr.yml / smoke-tests.yml Regressions on real-world specifications and older target frameworks
regression-tests.yml Platform-specific problems (paths, line endings, process handling) on Windows, Linux and macOS
msbuild.yml Packaging and build integration problems in Refitter.MSBuild
production-tests.yml Problems in what users actually install: the published tool, Docker image and NuGet packages, including breakage caused by new versions of dependencies or the .NET SDK

Other safeguards

  • Warnings are errors. src/Directory.Build.props enables TreatWarningsAsErrors, nullable reference types and the .NET analyzers for every project. The source generator also enables EnforceExtendedAnalyzerRules.
  • Generated code is checked for warnings in unit tests. BuildCSharp(warningsAsErrors: true) compiles generated code with warnings as errors for features such as deprecated schemas and XML documentation. The smoke tests don't do this: every smoke-test build passes WarningLevel=0, so they only catch compiler errors.
  • Static analysis and review. SonarQube Cloud quality gates and automated code review run on pull requests, followed by review from the maintainer.
  • Dependency updates. Dependabot and Renovate keep NuGet packages, GitHub Actions and dev containers up to date. Each update goes through the full CI pipeline, and the nightly production tests catch breakage caused by new releases of dependencies.
  • Definition of Done. CONTRIBUTING.md requires scenario tests with a compilation check for new features, a failing-without-the-fix regression test for every bug fix, tests for interacting options, new options being off by default, and documentation of new settings in the README, the .refitter file format docs and the JSON schema.
